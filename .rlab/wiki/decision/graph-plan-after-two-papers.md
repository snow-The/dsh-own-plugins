# 决策：先建评估器，再做小旋钮拓扑，最后做可回溯的 state-first

## 背景
读完两篇全文（`arxiv-2502.02533` MASS ✓、`arxiv-2608.26263` SKILL.state ✓）后，**原先"join 优先"的排序被证据推翻** ✗✓，改为下面这个顺序 ✓。

## 证据（每条都可回查知识页）
| 证据 | 出处 |
|---|---|
| **收益主要来自 prompt 而非拓扑** ✗✓：阶段 1 = **+6 分** ✓、拓扑 = **+3** ✓、阶段 3 = **+1.5** ✓ | MASS Fig 5 左 ✓ |
| MASS 的"拓扑"是**五块整数参数**（N_s 0–4 / N_a {1,3,5,7,9} / N_r 0–4 / N_d 0–4 / N_t {0,1} ✓），**顺序被规则钉死** ✓，**不是 DAG** ✗ | MASS Table 3 / App B.3 ✓ |
| **搜索建立在评估器上** ✓：影响力 I = E(a_i*)/E(a0*) ✓ → 剪枝 → 拒绝采样 ✓ | MASS 阶段 1–2 ✓ |
| SKILL.state 的**唯一稳健收益是 token** ✗✓（仓库 T=100：65,408 vs 1,062,387 = **16.2×** ✓）；准确率**短程输** ✗、开源权重**打平** ✗ | SKILL.state Table 1 / 6 / 7 / 8 ✓ |
| SKILL.state 的命门：**格式正确但内容错误的补丁永久不可纠正** ✗（无 transcript 交叉核对 ✗、无版本化 ✗、无 undo ✗） | 其 Sec 7 只承认一半 ✓，68% "Premature State Overwrite" 只对开源权重报 ✓ |
| **我们独有的能力** ✓：会话日志 append-only 可恢复 ✓ + M1 块存可原样取回 ✓ + `acp_decompress` ✓ | 本仓库现状 ✓ |

## 决定的顺序
### 0（新增，最高优先）建**评估器** ✗✓
- 理由：MASS 的三阶段**全都**要求可反复测量的验证集 ✓；没有它，拓扑搜索与 prompt 优化都无从谈起 ✓。我们现在**没有任何可自动判定的评测集** ✗
- 最小形态 ✓：10~20 个**可判定对错**的任务（不是"感觉更好"✗）＋ 一个打分器 ✓，输出 `{pass, tokens_in, tokens_out, wall_ms, cost}` ✓
- **证伪条件** ✗：若连 10 个可判定任务都凑不出，说明我们的工作流还不适合做自动优化 ✓ → 回到手工 ✓

### 1 busyloop：**小整数旋钮**拓扑 ＋ join ✓
- 照 MASS 的形状：暴露 `refine: 0..2` ✓、`debate: 0..2` ✓、`aggregate: 1..5` ✓（而非开放图 DSL ✗）
- ＋ ADK 的 `join` 语义 ✓（`concat' | 'json' | 'agent:<prompt>` ✓）
- **证伪条件** ✗：若在评估器上关掉旋钮与全开无显著差别 → 说明我们的任务不需要拓扑搜索 ✓ → 保留 join 即可 ✓

### 2 busyloop：**state-first 循环 ＋ 可回溯底账** ✓
- 抄 SKILL.state 的机制 ✓（`(P, Σ_t, O_t)` 进 ✓／`{state_patch, action}` 出 ✓／推理立即丢 ✓），**但加一条它没有的** ✓：每次状态转移都写进可回溯底账 ✓（原文可回查 ✓）
- **定位是成本/延迟手段** ✓，**不承诺质量提升** ✗（它的准确率证据不支持 ✓）
- **schema 必须小** ✓（照它 5 字段规模 ✓；Retail 那行证明大 schema 会让提示词变最长 ✗）
- **证伪条件** ✗：若 token 没有显著下降，或回查代价超过收益 → 放弃 state-first ✓

### 3 handoff：边语义 ＋ ADK 形状导出 ✓（不变 ✓）
- `delegations` 加 `kind/started_at/ended_at/status/tokens` ✓ → 已有执行图变可分析 ✓
- 定位是**可观测性** ✓，**不是**搜索能力的来源 ✓（与 MASS 的结论一致：图本身不是收益来源 ✗✓）

## 明确不做（本轮）
- 开放图 DSL ✗（MASS 证明小参数族就够 ✓）
- 用"感觉"代替评估器 ✗
- 把 SKILL.state 当质量提升来讲 ✗

## 未决 → 具体提案（批准即可执行 ✓）

### 评估器放哪 ✓
- **位置**：本仓库（`plugins`）的 `.rlab` ✓ —— 研究已在此聚集 ✓，不新建项目 ✗（避免第四个散落点 ✓）
- **结构**：`bench/tasks.jsonl`（任务 ✓）+ `bench/run.mjs`（打分器 ✓）+ `bench/results.jsonl`（结果 ✓）
- **每个任务必须是可判定对错** ✓（不是"感觉更好"✗），记录 `{id, prompt, check}` ✓；结果记 `{id, pass, tokens_in, tokens_out, wall_ms}` ✓

### 评估任务从哪来 ✗（关键约束）
**不能取我们日常在做的事** ✗ —— w8 的教训还热着：与训练同源的留出集**测不出泛化** ✗（"过拟合不是能力" ✓）。
- **提案**：从**外部、固定、已发布**的小任务集里取 10–20 个 ✓（确定性、有唯一正确答案 ✓、我们**没有**参与构造 ✓），在动手改插件**之前**就**冻结** ✗✓
- **记录纪律**：先按 lab 规范写 `rlab_experiment` 页，**把判据写在跑之前** ✓（本仓库既有规矩 ✓），再动手 ✓
- **基线先量** ✓：先在**当前**插件上跑一遍（不改任何代码 ✓）→ 得到基线 pass/token/wall ✓ —— 没有基线，后面任何"变好了"都是自说自话 ✗
